# STL import and export tests - how they work, and how to add one

**Scope:** the STL tests in the `FileIO` project. Implementation lives in
`FileIO\STL\StlImportBase.cs` and `StlExportBase.cs`.

Sixth format on the shared pattern: fixtures `StlImport`/`StlExport` (+ `[Explicit]`
`-future`/`-large`), folders `models\STLfile*`, extension `.stl` (+ `.3dm` in export folders),
namespaces `MX_STL_*` / `MX_STLEXPORT_*`, slack `MX_STL_RELTOL`/`MX_STL_ABSTOL`.

## STL-specific behaviour worth knowing

**STL is the thinnest format in the suite:** triangles and nothing else. No units, no layers, no
colors, no assembly structure, no curves or annotations. Everything meshable becomes one body;
everything else is dropped silently. The export baseline reads accordingly - the source's curve,
point and text vanish, and the breps arrive as meshes.

**Always `FileStl.Read` / `FileStl.Write` with explicit options**, never a bare
`RhinoDoc.Import`: without a dictionary the reader takes weld, split and units from the machine's
saved plugin profile, so results differ between machines.

**`STLModelUnits` is a dead option (RH-98713).** The reader parses it into a local that is never used again;
scaling comes from plugin state (the millimetre default, headless). Pinned here for the day it is
fixed. STL files carry no units of their own, which is why the option exists at all.

**`ExportOpenObjects` stays true** everywhere in this suite. False plus open geometry raises an
ungated modal error dialog - see the warning below for why a modal dialog is not a small problem.

**The structural checks** (no-baseline floor) split on the pinned `binaryfile` option:

- *Binary*: an 80-byte header, a uint32 triangle count, then exactly `count x 50` bytes. The size
  formula is the entire format, so it catches truncation to the byte.
- *ASCII*: the `solid`/`endsolid` envelope, balanced `facet`/`endfacet` and `outer loop`/`endloop`
  blocks, and exactly three numeric vertices per loop.

## The corpus

Generated by `FileIO\STL\AuthorStlCorpus.cs`. Five models: a binary box and the same box in
ASCII (their baselines are identical line for line - same geometry, both encodings, which is the
cross-check), two disjoint bodies in one file (the reader's `SplitDisjointMeshes` default puts
them back into two meshes), a faceted sphere, and a hand-written ASCII tetrahedron that is
deliberately not Rhino's own output - named solid, free-form indentation, non-unit normals.

Its volume is pinned at 133.333..., which is exactly 800/6, the determinant of the three edge
vectors. Wind those facets the other way and the mesh still reads as closed and still measures
133.333 - but negative. A baseline pinning a negative volume would be pinning the corpus author's
mistake rather than the reader's behaviour, which is how the first draft of this corpus was wrong.

## ⚠ Re-authoring a corpus: suppress input, or hang the machine

`RhinoDoc.WriteFile` over an **existing** `.3dm` asks the user something. In a headless test host
with `SuppressAllInput`/`SuppressDialogBoxes` unset, the author does not fail - it blocks forever,
and the blocked test host **cannot be killed**: neither `Stop-Process -Force` nor
`taskkill /F /T` will clear it, and it keeps a lock on `FileIO.dll` that stops every later build.
A reboot is the only way out.

Every author in this project therefore passes
`new FileWriteOptions { FileVersion = 7, SuppressAllInput = true, SuppressDialogBoxes = true }`.
Writing to a fresh folder hides the problem completely, which is exactly how it stayed hidden
until the first re-author. The exporters themselves (`FileStl.Write` and friends, which go through
`doc.Export`) are fine - they set suppression internally and overwrite happily.

MSBuildEnableWorkloadResolver=false dotnet test FileIO/FileIO.csproj -f net48 --no-build --filter "FullyQualifiedName~FileIO.StlImport"
